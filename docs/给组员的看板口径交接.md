# 看板调整口径 · 给组员的执行版

> 用途：组员在自己的版本上同步调整看板时，按这份口径执行，保证答辩时两边讲的是同一套数。
> 所有结论都附了实测数据，可直接引用。

---

## 一、总体结论

**大方向可行，可以同步开展。** 但下面 4 处必须按本文修改，否则会影响验收或答辩时答不上来。

### ✅ 可以直接做的部分（与我们结论一致）

1. KPI 卡片带环比
2. 销售趋势图支持粒度切换（日/周/月/季/年）
3. 品类销售额排名
4. 品类增长榜 + **小样本过滤**（我们已实现：品类成交额下限 1.0 万 R$；评分异动要求评论数 ≥ 20 条）
5. 订单报表多条件分页检索
6. **砍掉下单时段分布**（理由正确：全平台时段规律，店主无法改变流量，看了不能行动）
7. 精简用户等级分布、商品模块 KPI（但商品数/品类数不能回到写死值）

## 二、⚠️ 必须改的 4 处

### ① KPI 5 项漏了「热销商品数」→ 会直接影响 F1 验收

需求文档项目二 **F1 原文**：顶部 KPI 卡片（总销售额、总订单数、平均客单价、**热销商品数**）。

原方案提的 5 项是「总销售额、订单数、买家数、客单价、复购率」，**少了热销商品数**。

**改法**：F1 四项 + 复购率 + 环比 = 5 张卡。不能删「热销商品数」。

> 附注：我们接口里 `hotProducts` 实际是「区间内有销量的商品数」（全区间 = 32,951，2018-01~08 = 20,495）。建议前端标签写「有销量商品数」，写「热销商品数」容易被追问「怎么等于商品总数」。

### ② 「同比」在本数据集上算不出来 → 必须改成「环比」

实测 `/api/orders/stats?granularity=month` 的月度订单量：

| 月份 | 订单数 | 说明 |
|---|---|---|
| 2016-09 | **3** | 残月 |
| 2016-10 | 308 | 起步期 |
| 2016-11 | — | **缺月（数据里没有）** |
| 2016-12 | **1** | 残月 |
| 2017-01 | 789 | |
| 2018-08 | 6,452 | |
| 2018-09 | **1** | 数据截止残月 |

全量只有 **24 个月**，含 1 个缺月 + 2 个残月。2017 年做同比，分母是 3 单、1 单 → 会算出「+26000%」这种荒谬结果。

**改法**：
- 一律用**环比**（相邻等长区间），不用同比；
- 图表副标题标注周期口径；
- 排除 2016-09、2016-12、2018-09 三个残月，避免污染趋势线。

### ③ 「亚秒级响应」当前架构做不到 → 不要承诺

实测（H2 文件库 + 全表聚合）：`kpi` ≈ 10s、`orders` 分页 ≈ 9s、`alerts` ≈ 19s、`signals` ≈ 18s。

**做不到亚秒级。** 三条路径，按性价比排序：

| 方案 | 做法 | 评价 |
|---|---|---|
| **a. 预聚合表（推荐）** | 建 `t_daily_category_summary`（日 × 品类 × 卖家 的销售额/订单数/件数），导入时算好 | 查询降到毫秒级，一次做好长期受益 |
| **b. 内存缓存** | Spring Cache，TTL 5–10 分钟 | 改动小，第二次访问亚秒级；首次仍慢 |
| **c. 演示前预热** | 提前把各接口打一遍，并诚实说明首次加载 5–10 秒 | 零开发，但体验仍差 |

时间紧就做 b；想真解决就做 a。

### ④ 支付方式分布不建议完全砍掉

「信用卡绝对主导」这个判断是对的。实测占比：

| 支付方式 | 占比 |
|---|---|
| 信用卡 | **73.8%** |
| Boleto | 19.4% |
| 代金券 | 5.3% |
| 借记卡 | 1.4% |

F7 要求「新老用户占比**或**支付方式占比」，我们已有新老客占比满足 F7，所以砍支付不违规。

**但建议**：不要删，改成 **分期数分布**（`payment_installments`）。信用卡主导没信息量，但「几期分期最主流」有信息量，且能导向动作（主推 X 期免息）。

## 三、🔧 我们这边刚修掉的 2 个 bug（别照抄我们的旧实现）

### 1. 不传日期时，4 个环比恒为 `0.0`（假环比）

**现象**：`GET /api/orders/kpi` 不带日期 → `salesGrowth / ordersGrowth / avgGrowth / productGrowth` 全是 `0.0`，前端显示「↑ 0.0%」。

**原因**：日期为空时「上一期」无法推算，代码把上一期查询退化成**同一个全量区间** → 自己跟自己比 → 恒等于 0。

**已修**：无日期区间时环比返回 `null`，前端渲染「--」表示「无可比周期」。带日期时正常（实测 2018-01~08：销售额环比 **+47.0%**）。

### 2. 复购率三处数字不一致（同屏出现会被当 bug）

| 位置 | 时间窗 | 复购率 |
|---|---|---|
| `/orders/kpi` | 全量 | 3.1% |
| `/orders/kpi` | 2018-01~08 | 2.2% |
| 诊断卡文案 | 本期（近 90 天） | 1.8% |

**不是算错**（时间窗越长，复购机会越多，数值越高，符合逻辑），但**没标时间窗**，用户会认为是 bug。

**改法**：所有复购率旁边标注口径（如「近 90 天」），或全站统一时间窗。

## 四、📌 统一口径表（两边必须一致，答辩按这个讲）

| 项目 | 统一口径 |
|---|---|
| KPI 卡片 | F1 四项（总销售额 / 总订单数 / 客单价 / 热销商品数）+ 复购率 + 环比 = 5 项 |
| 增长率 | 一律**环比**（相邻等长区间），**不用同比**；图表标注周期 |
| 复购率 | 分母 = 唯一客户数（`customer_unique_id`）；健康线 20%；**必须标时间窗** |
| 金额单位 | **万 R$（巴西雷亚尔）**，全站禁止出现 ¥ |
| 支付方式 | 保留（可降级到二级页，或改成分期数分布） |
| 州分布 | 可保留，但**移到二级页**并标注「全平台口径，非本店」 |
| 补货建议 | 必须带「**基于销售趋势推测，非实时库存**」标注 |
| 图表标题 | **问题式**（「该多押哪个品类？」），不用名词式（「品类销售分析」） |
| 数据不可得项 | 库存 / 成本 / 毛利 / 流量 / 曝光 / 点击 / 转化漏斗 / 广告 ROI —— **一律不承诺、不出现** |
| 商品名 | 数据无商品名，用「中文品类 + product_id 后 6 位」代理，README 说明 |

## 五、🚧 协作边界

- 组员做自己的版本（`com.example.dashboard`），主交付版本是另一套，**不要在同一仓库、同一批文件上并行修改**，避免互相覆盖。
- 两边可以各自实现，但**上面这张口径表必须一致**，否则答辩时两个人讲出两个数很难看。
- 接口路径请按需求文档原路径实现：`/api/categories`、`/api/orders`、`/api/orders/kpi`、`/api/orders/ranking`、`/api/orders/stats`。我们这边原先用了 `/orders/categories`、`/orders/product-ranking`、`/orders/trend`，文档路径会 404，已补别名，**新写请直接用文档路径**。
