DataPeak 电商看板 · 人机协同方案

课程展示 / 答辩版 · 面向非专业开发者小组的人机协同分工、SOP 与 Prompt 指导

一、协同定位（一句话 + 为何本组尤其需要）

人机协同的本质是能力互补：人负责定方向、做判断、担责任；AI 负责出算力、做执行、跑规模。判断一项工作归属的准则只有一条——"此事是否需要价值判断或承担责任？需要→人；不需要且可标准化→AI。"

为何本组（非专业开发者）更需要显性的人机协同

  • 能力缺口由 AI 补齐：本组不擅长编码、调试、部署与数据清洗，这些恰是 AI 可稳定执行的环节，使小组能交付一个完整可运行的 Web 应用。
  • 风险由人兜底：需求定义、产品定位、数据真实性、对外口径与账号安全，必须由人判断与拍板，避免"AI 幻觉"直接变成交付物。
  • 协同需被记录：非专业开发者的优势在业务理解，劣势在技术细节；把"谁做了什么、谁拍了板"显性化，既是质量保障，也是本评分项的直接证据。

三、详细分工矩阵（非开发者视角，按阶段切分）

下表将项目全生命周期拆为六个阶段，逐项标注"人负责 / AI 负责 / 交接闸门"。闸门即人机边界的硬开关：越过闸门的事项必须由人确认，AI 不得擅自执行。

阶段人（本组组员）负责AI（协同工具）负责交接闸门
需求与定位界定目标用户（看店店主"林姐"）、明确"每张图对应一个动作"的取舍标准、确定产品边界将口头需求整理为结构化需求卡草稿人拍板 产品定位与砍图决策不可由 AI 代定

排错与构建提供完整报错与环境信息、确认命令安全性后执行定位报错根因、给出可复制命令（如代理 502 走 --noproxy、JAR 占用先 taskkill）人确认 涉及删除/登录/账号的命令必须人执行
验收与展示浏览器实测、答辩口径、最终结论、对外表达生成验收清单草稿、PPT 与文档初稿人拍板 对外口径与真实性由人兜底
安全与伦理账号/密码/token 管理、隐私红线、一票否决在权限内调用，不接触凭据红线 凭据绝不进文件/日志，账号操作须本人

四、协同 SOP 撰写指导（含本项目现成范例）

4.1 什么是 SOP，为何人机协同需要它

SOP（标准作业流程）是把"人机会如何配合完成一类任务"固化成可复用的步骤清单。对与非专业开发者小组，SOP 的价值在于：把"靠临场发挥"变成"按步骤走"，降低对个人的技术依赖，并保证每次协同的质量一致、可追溯。

4.2 SOP 的标准写法（字段模板）

字段说明（撰写要点）
编号 / 名称唯一标识 + 一句话说明用途，如"SOP-DV-01 需求转实现"
适用场景什么情况下启用本流程，避免误用
角色与步骤逐条写明"谁（人/AI）做哪一步"，并标注产出物
闸门 / 复核点在哪些步骤必须停下来由人确认
产出与记录流程结束交付什么，留下什么以供追溯

4.3 本项目可直用的四个 SOP 范例

SOP-DV-01　需求转实现流程
  • 人：写需求卡——目标用户、要解决的一个动作、明确不要什么。
  • 人：将需求卡转为结构化 Prompt 交给 AI（见第五章模板）。
  • AI：生成代码并说明改动点（先给差异，再给代码）。
  • 人：本地按"看到 XX 才算完成"的验收标准运行确认。
  • 闸门：涉及产品定位 / 砍功能 → 人拍板；纯技术实现 → AI 可直接做。
  • 产出：《需求卡》+ 代码 + 验收记录。
SOP-DV-02　AI 产出人工复核清单
  • 真实性：数据有无编造？推测项是否已标注？
  • 边界：是否越界承诺了拿不到的数据（库存 / 成本 / 流量 / 投放）？
  • 一致性：是否与已定产品定位（林姐 / 5 张图）冲突？
  • 一票否决：任一项不通过，打回 AI 重做，不计为交付。
SOP-DV-03　排错协同流程
  • 人：复制完整报错 + 环境（系统 / 端口 / 代理状态）贴给 AI。
  • AI：定位根因 + 给出可复制命令。
  • 人：确认命令安全（不删库、不替你登录）后执行。
  • 人：验证解决，并将该坑写回 Skill / Memory（反馈闭环）。
SOP-DV-04　数据口径把关流程
  • 适用：任何涉及"数据含义"的表述（图表标题、答辩话术、文档）。
  • 规则：Olist 数据集拿不到的（库存 / 成本 / 流量 / 投放）一律不承诺。
  • 规则：凡推测（如"基于销售趋势推测，非实时库存"）必须显式标注，不得伪装成确定结论。

五、Prompt（提示词）撰写指导（含本项目现成范例）

5.1 为何非专业开发者更需结构化 Prompt

AI 的输出质量高度依赖输入的清晰度。非专业开发者若只说"帮我做个看板"，AI 会自行假设技术栈与范围，结果往往跑偏。采用五段式结构后，即使不懂代码，也能稳定拿到可用产出。

5.2 五段式 Prompt 模板

[角色] 你是一名资深的 ___ 工程师，熟悉 ___。 [背景] 我们的项目是 ___，当前技术栈/环境是 ___，已约定 ___。 [任务] 请帮我 ___（具体到可验证的结果）。 [约束] 不要 ___；必须 ___；输出 ___。 [输出格式] 先给"改动点/思路"，再给可复制的代码/命令，最后给"验收标准"。

5.3 本项目三个可直抄的 Prompt 范例

范例 1 · 后端接口实现
[角色] 你是一名资深 Java / Spring Boot 工程师。 [背景] 项目 DataPeak 是给看店店主用的电商看板，后端用 Spring Boot + H2 文件库， 数据库自举在 DatabaseInitializer，金额已转"万 R$"。 [任务] 新增一个接口，返回近 12 个月销售额趋势（月份、销售额、订单量）。 [约束] 不改动产品定位；SQL 用显式列名；金额单位保持"万 R$"。 [输出格式] 先给改动点，再给 Controller/Service 代码，最后给 curl 验收命令。
范例 2 · 前端图表修改
[角色] 你是一名前端工程师，熟悉原生 JS + ECharts。 [背景] 前端 API 基址必须写 http://127.0.0.1:8080/api（不能写 localhost，否则被 CSP 拦截）。 [任务] 把"品类涨跌榜"图改为存量+增量合并的横向条形图，点击可看明细。 [约束] 不要新增第三方库；颜色遵循红涨绿跌（中国习惯）。 [输出格式] 先给改动点，再给 JS 片段，最后给浏览器验收步骤。
范例 3 · 排错求助
[角色] 你是一名运维/排错助手。 [背景] 本机有 Clash 代理；命令行 curl http://localhost:8080 走代理返回 502。 [任务] 后端 Spring Boot 已启动但本地访问 502，请定位原因并给命令。 [约束] 不要让我关闭代理；给出可直接复制的命令；说明每条命令的作用。 [输出格式] 先给原因，再给命令清单，最后给如何确认已解决。

5.4 常见错误清单（写 Prompt 时自查）

错误写法后果与修正
"帮我做个看板"太模糊 → 补【任务】与【背景】，写明要什么结果
不写项目背景AI 瞎编技术栈 → 必写当前环境与技术约定
不写约束AI 承诺做不到的（如实时库存）→ 用【约束】划红线
不要输出格式拿到一大段难用的文字 → 强制"先思路/再代码/后验收"
一次塞太多任务产出失控 → 一个 Prompt 只解决一类可验证结果

六、协同规范（落地红线，调整项目前先确立）

本组人机协同七条基线（建议在展示中作为"我们的协同制度"呈现）：
  1. 决策闸门：AI 直做=代码/调试/文档初稿/重复排错；必须人确认=定位/砍功能/对外口径/隐私账号/数据真实性。
  2. 真实性红线：数据不编造；推测必标注；无字段（库存/成本/流量/投放）不承诺。
  3. 先试点后推广：改项目先动一个模块验证跑通，再全量复制，不一开始追求全场景自动化。
  4. 先有闸门再求效率：初期走"AI 建议、人全审"，靠审计与抽检调优后再放宽。
  5. 反馈闭环（HITL）：人修正的内容回流到 Prompt / 规则 / Skill，避免重复趟坑。
  6. 隐私安全：token / 密码不进文件与日志；账号登录等须本人操作。
  7. 可追溯：保留对话与关键决策点，答辩时能说清"这一步是人定还是 AI 执行"。
